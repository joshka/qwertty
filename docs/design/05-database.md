# Design 05 — The sequence database

Schema, identity, citations, fixtures, support status; what it generates; what it is not.
Implements R-DB-1–5, R-CONF-1, R-SEC-4; addresses FM-E5, FM-X8. Companion one-pager:
[conformance-target-interface.md](conformance-target-interface.md) (ghostty-rs deliverable).

## Shape

**TOML, one file per protocol family** (`db/csi.toml`, `db/osc.toml`, `db/dcs.toml`,
`db/kitty-keyboard.toml`, `db/kitty-graphics.toml`, `db/iterm2.toml`, `db/finalterm.toml`,
`db/rio.toml`, `db/mux-passthrough.toml`, …), fixtures as sibling files under
`db/fixtures/<family>/`. TOML earned its place: the prototype's sequence tables audited clean
in exactly this shape and are harvestable (audit trust map); the errors lived in *values*
(fabricated reports), which schema rules below make structurally harder.

### Entry schema — the whole thing

```toml
[[sequence]]
id          = "csi.cup"                # stable, namespaced, never reused or renamed
name        = "Cursor Position (CUP)"
description = "Moves the cursor to the given row and column."   # one plain-English sentence:
                                       # what this does, readable with no VT background;
                                       # the generated reference leads with it
direction   = "host-to-terminal"       # | "terminal-to-host" | "bidirectional"
syntax    = "CSI Pr ; Pc H"            # canonical form, ECMA-48 notation
params    = [{ name = "Pr", kind = "number", default = 1 }, { … }]
refs      = [{ doc = "ecma48", section = "8.3.21" },
             { doc = "xterm-ctlseqs", anchor = "CUP" }]
fixtures  = ["cup_home.seq", "cup_5_10.seq"]
replay    = "safe"                     # | "modal" | "destructive"  (FM-X8)
responds  = "csi.cpr"                  # id of the reply sequence, if this is a query
notes     = "1-based; clamps at margins per DEC STD 070 …"
```

Nine fields plus notes (`description` added at the maintainer's gate read — the schema
originally lacked any "what does this do" prose, which the generated reference needs and a
schema reader immediately misses). **Deliberately absent**: `confidence` (audit: uncorrelated with
correctness — an entry's trustworthiness *is* its refs+fixtures, FM-E5), `support_tier` /
per-terminal support (lives in conformance results, below), `owner_crate`/Rust cross-links
(the prototype's registry-to-code strictness generated busywork; generation, below, points
the other way), and free-form `provenance` (git history is provenance).

- **IDs** are the public contract (ghostty-rs P0): `family.mnemonic`, lowercase, stable
  forever; corrections change fields, never ids; a wrong id is deprecated via
  `superseded_by`, not deleted.
- **`refs`** resolve against `db/sources.toml` — one table mapping doc keys to full
  citations (title, URL, retrieval date, archive link). Every entry needs ≥1 ref; report-
  direction entries need a ref **or** a live capture (next section) — never neither.
- **`docs/`-free**: prose beyond `notes` belongs in generated documentation, not the db.

### Fixture model

- `.seq` files keep the prototype's escaped-text convention (`\e`, `\xNN`, `\\`), now
  specified normatively in `db/fixtures/FORMAT.md` including the trailing-LF rule (audit
  finding 6: two auditors missed the convention; it gets a spec and a lint).
- Every fixture header line declares direction and origin:
  `#! direction=terminal-to-host origin=capture:ghostty-1.2.0 date=2026-07-06`
  or `origin=spec:xterm-ctlseqs`. **Report-direction fixtures with `origin=spec` require a
  quoted spec line in the entry's notes; `origin=capture` requires a capture log in
  `db/captures/`.** This is the quarantine rule made permanent (R-DB-3).
- Loadable standalone: format doc + `.seq` files + `sources.toml` are self-sufficient; the
  unescape routine is ~20 lines any consumer can write (ghostty-rs ask 1 satisfied without
  our build system).
- Harvest plan: prototype host→terminal fixtures import after mechanical unescape +
  per-family re-verification against the audit's verdict tables; the discard list
  (audit README) is applied wholesale; all terminal→host fixtures enter only through the
  capture flow.

### Support status = conformance results, not registry fields

`conformance/results/<terminal>/<version>.toml` — generated by the runner, checked in, keyed
by sequence id × terminal identity (the R-CAP-5 identity model). The caniuse dataset and
support matrix are *renderings* of these files. Hand-editing a result file is the process
smell the schema exists to prevent: humans write entries and citations; machines write
support claims (FM-C9's advertise-above-evidence, applied to ourselves).

## What it generates (R-DB-4)

1. **docs.rs protocol reference** — one page per family from entries + refs + fixtures;
   every claim traceable (build step in the docs pipeline, not runtime).
2. **Conformance test cases** — command entries with `replay = "safe"` fixtures become
   runner probes; `responds` links pair queries with expected reply syntax.
3. **The caniuse dataset** — results files above.
4. **Optionally, code skeletons** (sequence-const tables for old families) — generation flows
   db→code; the db never reads from code and is **not a runtime lookup table**.

Tooling lives in an unpublished workspace tool (`tools/qdb`: validate, lint, generate,
capture) — the split ADR-0014's rule actually licenses: different audience, no shared semver.

## The live-capture harness (R-CONF-1, before the full runner)

`qdb capture` drives one target (real terminal under a PTY, or in-process ghostty-rs) with
the query entries, records raw reply bytes + identity probe results into `db/captures/`, and
mints report-direction fixtures with `origin=capture:` headers. This is one binary crank:
it replaces the quarantined fixtures and seeds conformance results in the same pass. It is
also the blocking probe-drain-timeout loop the OQ-1 one-shot API later packages —
three deliverables, one core.

## Grokkability acceptance (R-DB-5)

The schema definition above is the whole schema — this section of this document *is* the
ten-minute read. A new entry is writable from it alone. `qdb validate` enforces: id format,
ref resolution, fixture existence + header/direction agreement, replay classification
present, reply linkage well-formed.

## Alternatives considered

- **JSON/JSON-Schema**: better tooling ubiquity, worse human diff/review ergonomics for a
  hand-curated corpus; TOML's table-array reads as a record card, and review-ability is the
  binding constraint (FM-E5 happened because nobody could review 400 fixtures).
- **One monolithic file**: merge-conflict magnet; per-family files match how sources and
  reviewers partition.
- **Support tiers in entries** (prototype's Known→Native ladder): rejected — it conflates
  "what the world defines" (db) with "what qwertty implements" (code/tests) and "what
  terminals do" (results); the prototype needed gap-report machinery to police the
  conflation.
- **Database as runtime data** (terminfo-shaped): rejected in the mission itself; runtime
  lookup reintroduces the stale-database failure class (FM-C1) one layer up.
