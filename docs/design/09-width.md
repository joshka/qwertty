# 09 — Width measurement (design + spike; CHECKPOINT)

Status: **DECIDED (maintainer, 2026-07-12).** The measured data and options are below; the decision
is recorded here.

## Decision (maintainer, 2026-07-12)

1. **Mechanism: HYBRID.** Static unicode-width baseline + a per-identity deviation table for the
   known-hard clusters + 2027 awareness.
2. **Mode 2027: OBSERVE only.** qwertty detects 2027 support/state and keys the deviation lookup on
   it; it does **not** enable 2027 during session setup (no mode-ledger change).
3. **Deviation-table home: db/-owned data.** qdb owns the table as `db/` data, regenerated by the
   permanent width probe (A4); the library embeds it at build time.
4. **API:** `width_of(&str, &Capabilities) -> usize` as the entry point (author's default, open to
   revision in PR review); a `char`/grapheme split is deferred until a consumer asks.
5. **Baseline dep:** the `unicode-width` crate is acceptable as the compiled baseline.

Follow-on: **A4** (width probe as a permanent runner feature + `db/` deviation-table regeneration)
lands first — it produces the data. **C2** (library `width_of`) consumes it. Task specs are
maintainer-local records.

The measured data and the options that led to the decision follow.

## Why this exists

Terminal applications must know how many columns a string occupies to lay out anything — status
lines, tables, wrapping, cursor math. The naive answer is a compiled unicode-width table
(`unicode-width` crate). The problem: real terminals **disagree with that table and with each
other** on a specific, bounded set of clusters, so a table-only answer is knowably wrong for some
terminal on some input.

This was rabbitui's concern until the maintainer reversed it (60/40): *"knowing deeply which
terminal and version is in use belongs at the terminal layer."* qwertty owns terminal identity and
capability probing, so width measurement — which is identity- and mode-dependent — belongs here.
The playbook (§10) sketched the target API:

```rust
// consults identity + 2027 state carried in Capabilities; not yet implemented.
fn width_of(s: &str, caps: &Capabilities) -> usize;
```

## The spike

Method (the established one): home the cursor, print one grapheme cluster, query CPR, read
the column it landed on — the rendered advance. Run the classic disagreement corpus (ASCII,
CJK, emoji: single / ZWJ / skin-tone / flag, combining marks, VS15/VS16, zero-width) against
every conformance target, with mode 2027 (grapheme clustering) off and — where the terminal
honours it — on. Vehicle: a throwaway `qdb width-spike` harness over the A1 Target adapters
(preserved as a maintainer-local record; it seeds A4 if the decision needs it).

Data: distilled and per-target tables are maintainer-local records. Five targets, macOS,
2026-07-12: tmux 3.7b, ghostty (via betamax), kitty 0.39.1, alacritty, wezterm.

## What the data shows

1. **A large stable core.** 8 of 12 corpus classes — ASCII, CJK, Hangul, single emoji, combining
   marks, VS15, bare symbol, zero-width — matched the static table on **every** terminal. In real
   text these dominate. The table is right there, for free.

2. **A small, named deviating set.** Only ZWJ sequences, emoji skin-tone modifiers,
   regional-indicator flags, and VS16 emoji presentation deviate — and terminals disagree with
   each other, not just with the table:

   No single static number is right for all of them at once: ZWJ family is 2 on tmux/wezterm but 8
   on kitty/alacritty; VS16 is 2 on tmux/kitty but 1 on alacritty/wezterm. A table must pick a side
   and be wrong on the other — the exact failure the reversal was about.

3. **Mode 2027 is decisive but not yet widespread.** Only ghostty (1 of 5) recognises it. With
   2027 on, ghostty collapses every cluster to grapheme-width 2 — the clean model the ecosystem
   is moving toward, but not where most terminals are today.

4. **Identity keying can't always use XTVERSION.** alacritty answers no XTVERSION, so an
   identity-keyed table must fall back to the env hint (`TERM`, `TERM_PROGRAM`) for terminals that
   don't self-identify.

## The three options

### A. Static (unicode-width table only)

- **Cost:** zero. No terminal I/O, no state, pure function.
- **Correctness:** right on the stable core; **knowably wrong** on the deviating set for some
  terminal on some input, and *cannot* be right for all terminals at once (they disagree). Ships the
  behaviour the reversal set out to fix.
- **Verdict:** insufficient alone — but it is the correct *baseline*.

### B. Measured (probe every string at runtime via CPR)

- **Cost:** a synchronous terminal round-trip per measured string. Unacceptable in a render/layout
  loop (single-digit-ms per probe × many strings per frame); needs a live tty, so it breaks for
  piped, headless, or not-yet-connected output. Racy with application output.
- **Correctness:** perfect for the actual terminal, live.
- **Verdict:** unusable per-frame. Viable only as **offline calibration** — which is exactly what
  feeds option C.

### C. Hybrid (static baseline + identity-keyed deviation table + 2027 awareness) — recommended

- **Shape:** `width_of(s, caps)` sums cluster widths from the compiled unicode-width baseline,
  except for clusters in the known-deviating set, where it consults a compiled per-identity
  deviation table (keyed on terminal identity + version + 2027 state, populated offline from
  conformance width probes). When the terminal honours 2027 and it is active, prefer the
  grapheme-cluster model (each grapheme = its 2027-defined advance). Unknown terminal → fall
  back to the static baseline (honest: no invented per-terminal claim without evidence).
- **Cost:** build + maintain the deviation table (this spike is its seed; **A4** makes the width
  probe a permanent runner feature and regenerates the table as targets are added). A small
  per-cluster lookup at width time; the stable core stays a pure table sum.
- **Correctness:** free and right on the core; right on the hard clusters for known terminals;
  degrades safely to the baseline for unknown ones; tracks 2027 where honoured.
- **Verdict:** matches the measured reality — bounded deviation, identity/2027-dependent — and
  the playbook's sketch. **Recommended.**

## Recommendation

**Hybrid (C).** The data is unambiguous: the static table is right for the bulk of text and
provably cannot be right for the small deviating set across terminals, which is precisely
identity- and 2027-dependent. A hybrid keeps the zero-cost baseline, corrects the known-hard
clusters per terminal from measured evidence, and stays honest (baseline fallback) where there is
no evidence.

## For the maintainer to decide (checkpoint)

1. **Ratify static / measured / hybrid.** (Recommendation: hybrid.)
2. **Deviation-table storage & seam:** does the per-identity table live in the library (compiled
   from a checked-in data file the conformance runner regenerates), matching how `Capabilities`
   already carries identity? Or as `db/` data qdb owns and the library embeds?
3. **2027 policy:** when a terminal supports 2027, does qwertty *enable* it as part of session setup
   (so width becomes deterministic), or only *observe* it and key the table on the observed state?
   Enabling it is a mode-ledger change (design 01) and interacts with the render surface.
4. **API surface:** confirm `width_of(&str, &Capabilities) -> usize` as the entry point, plus
   whether a `str_width` / `char_width` / grapheme-iterator split is wanted now or deferred.
5. **`unicode-width` dependency:** acceptable as the baseline crate, or vendor a table?

On the answer: **C2** (implementation) and **A4** (width probe as a permanent runner feature +
table regeneration) get written as new task files. Nothing ships before then.
